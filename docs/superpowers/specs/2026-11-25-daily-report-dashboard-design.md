## 1. 배경과 목적

- 회사는 노션 초창기부터 노션을 써 왔다. 자율성이 높고 마크다운이라 작성이 편해서다.
- 개인별 업무목록, 제품별 QA목록 등 여러 페이지를 시도했지만 대부분 정착하지 못했다. 지금 실제로 쓰는 것은 두 페이지뿐이다.
  - **일일 업무보고** (예: `[담당자] 실장 업무보고 - 2026년 11월24일(화)`)
  - **본영업 목표매출 관리 현황** (예: `본영업 목표매출 관리 현황 - 2026년 11월 23일(월)`)
- 이 두 페이지를 노션이 아닌 자체 시스템으로 옮기라는 지시가 있었다. **[결정]**
- 이관 이유:
  1. **비용 절감** — 노션 비용은 월 5만 원 정도. 가장 큰 이유. (이관할 가치가 있는지의 판단은 이번 기획 범위가 아님) **[결정]**
  2. **막막함 해소** — 노션은 자율성이 너무 높아서 무엇을 어떻게 만들지 막막하다. 그래서 범용 기능 위에 **업무관리에 특화된 컴포넌트**(예: 매출관리 전용 컴포넌트)를 갖춘 "업무관리 특화 노션"을 만든다. **[결정]**
- 노션의 기본 기능(범용 데이터베이스 포함)은 웬만하면 모두 넣는다. **[결정]**
- 지금 매출 페이지의 숫자는 기존 **업무관리시스템**(사내 웹 시스템)에 있는 값을 사람이 노션으로 옮겨 적고 있다. 업무관리시스템은 엑셀 내려받기가 되고(영업 건마다 고유번호 있음), API는 "제공할 수 있다"는 말까지만 들었다. **[결정]**

## 2. 목표 · 비목표 · 실패 기준

### 목표
- 노션의 기본 기능(페이지, 블록 에디터, 데이터베이스와 여러 보기 등)을 갖춘 사내 워크스페이스. **[결정]**
- 그 위에 업무 전용 화면 3개: 캘린더 → 그날의 일일 업무보고 / 본영업 목표매출 관리 현황. **[결정]**

- 날마다 기록이 남는다. 지난 날짜를 열면 그날 상태를 그대로 볼 수 있다. **[결정]**
- 지난 페이지도 고칠 수 있고, 고친 기록(누가, 언제, 무엇을)이 남는다. **[결정]**

### 실패 기준 (기술적으로 동작해도 실패로 보는 것)
- 노션보다 쓰기 불편하다.
- 여전히 누군가 매출 숫자를 손으로 옮겨 적어야 한다 (엑셀 올리기 한 번은 허용, API가 생긴 뒤에는 그것도 없어야 함).
- 다시 "무엇을 써야 할지 막막한" 상태가 된다.

### 범용 기능과 "막막함"의 균형 **[제안]**
범용 데이터베이스까지 넣으면 노션처럼 다시 막막해질 위험이 있다. 그래서:
- 로그인하면 **캘린더(업무 화면)**가 첫 화면이다. 빈 워크스페이스가 아니다.
- 업무 페이지는 정해진 틀과 전용 블록으로 시작한다.
- 범용 페이지·데이터베이스는 사이드바의 별도 영역에서 쓴다. 업무 화면을 쓰는 데 범용 기능을 알 필요가 없다.

## 4. 구현 방식

### 4.1 큰 방향
세 가지를 검토했고, 사용자는 **B. 업무 전용 블록이 있는 노션형 에디터**를 골랐다. **[결정]**

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 고정 틀 + 마크다운 입력칸 | 칸 고정, 글은 마크다운 칸, 매출은 자동 | 가장 빠르고 싸다 | 칸 변경에 개발자 필요. 노션 같은 작성감 없음 |
| **B. 업무 전용 블록이 있는 노션형 에디터 (선택)** | 노션처럼 쓰다가 `/`로 블록 삽입, 업무 전용 블록 제공, 틀로 시작 | "업무관리 특화 노션"에 가장 가깝다 | A보다 개발이 크다 |
| C. 오픈소스 노션 대체재 설치만 | 노션 비슷한 프로그램 설치 + 데이터 넣는 프로그램 | 에디터를 거의 공짜로 얻음 | 계산하는 전용 블록이 어렵고, 막막함이 그대로 |

### 4.2 출발점: litpage 코드를 가져와 고쳐 쓴다 **[결정]**
사용자 요청에 따라 [litpage](https://github.com/litmers-dev/litpage)를 BlockNote와 비교했고, **litpage**로 정했다.

- **포크하지 않는다.** litpage 코드를 이 저장소로 가져와 독립적으로 고친다. 원본과 연결하지 않고 업데이트도 따라가지 않는다. MIT 라이선스이므로 원본 저작권 고지(`LICENSE`, `THIRD_PARTY_NOTICES.md`)는 남긴다. **[결정]**
- **기술은 그대로 따르지 않는다.** litpage 시스템을 참고하되, 기술 스택은 이 시스템에 맞게 다시 고른다(8장). **[결정]**
- **가져오는 범위는 화면과 화면 쪽 공유 로직.** 메인 서버를 Python(FastAPI)으로 정했으므로 litpage의 TypeScript 서버는 쓰지 않고, litpage 화면이 호출하는 API 규격에 맞춰 Python 서버를 새로 만든다(8.2). **[결정]**
- 노션식 `/` 메뉴, 마크다운 단축키, 사용자 정의 블록은 유지한다. **[결정]**

**litpage를 살펴본 결과** (2026-11-25, 저장소 `f55fead` 기준)
- 에디터 라이브러리가 아니라 **노션 같은 워크스페이스 전체**다. 블록 에디터(41종 블록, `/` 메뉴, 마크다운 단축키, 끌어서 옮기기, 멘션, 댓글, 제안 편집, 버전 기록), 데이터베이스(표·보드·목록·갤러리·캘린더·타임라인·차트·대시보드·피드·폼·지도 보기, 수식, 관계, 롤업, 자동화), 권한, 실시간 공동 편집, REST API·웹훅이 들어 있다. 한국어 화면을 지원한다.
- 구성: React 19 + Vite(화면), Node.js 26 + Hono(서버), SQLite 파일 하나(저장), WebSocket(실시간). 에디터는 외부 라이브러리 없이 직접 만들었다. 블록은 `registerBlock`, 데이터베이스 보기는 `registerView`로 추가한다.
- 코드 규모: 서버 약 4만 2천 줄, 화면 약 9만 3천 줄, 화면·서버 공유 로직(`packages/shared`: 레코드, 편집 연산, 권한, 수식 엔진, 동시 편집 병합) 약 1만 6천 줄.
- **주의할 점:** 2026-10-23 첫 공개, 커밋 8개, 버전 0.1.0. AI 코딩 에이전트가 약 21시간 만에 만든 실험 프로젝트로, 저장소 스스로 "연구·시연용, 있는 그대로 제공"이라고 밝힌다. 그래서 본격 개발 전에 검증한다(6.2 0단계).

## 5. 화면 구성 — 업무 화면 3개 **[결정]**

```
첫 화면: 1depth 캘린더 ──날짜 클릭──▶ 2depth 일일 업무보고 (그날)
                                 └──▶ 2depth 본영업 목표매출 관리 현황 (그날)
사이드바: 범용 페이지·데이터베이스 영역 (노션 기본 기능)
```

### 5.1 캘린더 (1depth)
- 월 단위 달력. 날짜를 누르면 그날의 두 페이지로 들어간다.
- 날짜 칸에 보여 줄 것 **[제안]**: 업무보고·매출 페이지 작성 여부, 그날 매출 증감액(예: `+22,427,592 ▲`)
- 오늘 날짜로 바로 가는 버튼.

### 5.2 일일 업무보고 (2depth)
노션 원본 구성: 인사 관리 → 주요보고 & 오늘 업무(주요 보고, 오전, 오후).

| 영역 | 데이터 출처 | 블록 |
|---|---|---|
| 인사 관리 (구인 사이트, 직군별 채용 현황, 지원자 수) | **직접 입력** — 업무관리시스템에 없음 **[결정]** | 채용 현황 블록 |
| 주요 보고 | **직접 작성** (마크다운) **[결정]** | 기본 글 블록 |
| 오늘 일정 (오전/오후 시간대별) | **업무관리시스템에서 가져옴** **[결정]** | 일정 블록 |

- 새 날짜 페이지는 틀로 시작하고, 직접 입력하는 블록(채용 현황, 주요 보고)은 직전 작성일 페이지의 최신 내용을 이어받는다. **[제안]**
- 일정 블록은 가져온 일정을 보여 주되, 사람이 항목을 추가·수정할 수 있다. **[제안]**
- 페이지는 "날짜 + 작성자"로 저장한다. 지금은 작성자가 한 명이라 한 페이지만 보이고, 사람이 늘어도 구조를 다시 짜지 않는다. 일정은 작성자(담당자) 기준으로 가져온다. **[제안]**

### 5.3 지난 페이지 수정과 기록 **[결정]**
- 지난 날짜 페이지도 고칠 수 있다(직접 쓴 글, 채용 현황, 변동 구분).
- 고칠 때마다 기록을 남긴다: 누가, 언제, 무엇을 바꿨는지. 이전 버전을 열어 볼 수 있다. (litpage 화면의 버전 기록 기능을 쓰고, 기록 저장은 Python 서버에서 구현)
- 업무관리시스템에서 온 숫자(변동사항, 매출 요약, 계약·매출·수금, 영업활동, 일정 원본)는 그날 스냅샷으로 고정된다. **[제안]**
- "확정"이나 잠금 기능은 두지 않는다. 노션에도 없던 절차를 늘리지 않기 위해서다. **[제안]**

### 5.4 본영업 목표매출 관리 현황 (2depth)
노션 원본 구성: 접힌 섹션(매출 현황, 영업활동 관리, 일별 현황) → 2026년 본영업 매출 요약 → 변동사항 표 → 관리 매출 현황.

- **대상:** 본영업 두 가지(본영업 Ent., 본영업 Cloud) 영업 건만 올라간다. **[결정]**

| 영역 | 데이터 출처 | 블록 |
|---|---|---|
| 매출 요약: 오늘 증감액, 목표 매출, 목표 대비 예상(%), 4분기 목표/현황, 이번 달 목표/현황 (▲▼ 증감) | 목표 금액은 설정값, 현황은 자동 계산 | 매출 요약 블록 |
| 변동사항 표: 고객명, 구분, 제품, 순매출, 증감액, 확도, 가중치, 매출 구분, 매출일정 (바뀌기 전 값은 "기존: …"으로 함께 표시) | 자동 생성 (그날 스냅샷을 직전 기록일과 비교) | 변동사항 블록 |
| 계약·매출·수금 현황: 이번 달 완료/예정을 3단계 막대그래프로, 본영업 Ent./Cloud별 건수·금액 | 업무관리시스템 | 계약·매출·수금 블록 |
| 영업활동 기록: 고객별 카드(시각, 고객, 제품, 주 내용, 연락 상대, 확도/단계, 협력사, 매출일/수금일, 목표매출, 영업관리 내용) | 업무관리시스템 | 영업활동 블록 |
| 메모 | 직접 작성 | 기본 글 블록 |

- 접힌 섹션 3개의 정확한 내용은 사용자도 모른다. 업무관리시스템 화면(계약·매출·수금 그래프, 영업활동 카드)과 비슷한 내용으로 추정한다. **[확인 필요]**
- 블록은 접기/펼치기가 된다. **[제안]**
- 사장님이 모니터에 띄워 보시므로, 숫자와 그래프가 멀리서도 읽히는 크기로 만든다. **[제안]**

### 5.5 숫자 규칙
- **변동사항 표의 "기존"**: 바뀌기 전 값. 예: 목표매출 상향 시 `기존 [금액] → [금액], 증감 [금액] ▲`. **[결정]**
- **오늘 증감액**: 그날 스냅샷을 직전 기록일 스냅샷과 비교해 생긴 변동의 증감액 합. **[제안]**
- **목표 대비 예상**: 가중치를 곱한 값이 아니라 절대 금액 기준. **[결정]** 정확한 계산식(어떤 건을 더하는지)은 **[확인 필요]**.
- **확도와 가중치**: 서로 다른 지표다. 지금은 화면에 보여 주기만 하고 계산에 쓰지 않는다. **[결정]**
- **증감액의 기준 금액**: 순매출로 본다. **[제안, 확인 필요]**

### 6.2 진행 단계 **[제안]**
- **0단계 — litpage 검증 (1~2일):** 원본 그대로 사내 PC나 테스트 서버에 띄워 확인한다. 기준을 못 넘으면 BlockNote로 바꾼다.
  - 한국어 입력(조합 중 글자 깨짐), 표·데이터베이스 보기, 모바일 화면이 쓸 만한가
  - 들어 있는 테스트가 통과하는가
  - 전용 블록 하나(예: 채용 현황)를 실제로 붙여 볼 수 있는가
  - 회원가입을 끄고 관리자가 만든 계정으로만 로그인하게 할 수 있는가
- **1단계 — 화면 가져오기와 Python 서버 구축:** litpage 화면과 공유 로직을 이 저장소로 가져오고(저작권 고지 유지), litpage 화면이 호출하는 API를 FastAPI + PostgreSQL로 새로 구현한다. 이 계획에서 가장 큰 작업이다.
  - litpage 서버에는 API 모듈이 40개 안팎 있다. 처음부터 전부 옮기지 않고, 업무에 필요한 기능(로그인, 페이지·블록 편집, 데이터베이스와 기본 보기, 권한, 수정 이력, 실시간 동기화)부터 옮긴다. AI 기능, 공개 사이트, 자동화 같은 나머지는 필요할 때 추가한다. **[제안]**
  - 서버로 옮긴 공유 로직은 화면 쪽 TS 코드와 같은 테스트 케이스로 결과가 같은지 확인한다. **[제안]**
- **2단계 — 업무 화면과 엑셀:** 캘린더·업무보고·매출 화면, 전용 블록, 데이터 작업 프로세스(엑셀 올리기, 스냅샷, 변동 분류), 사내 서버 배포, 계정.
- **3단계 — 자동 동기화:** 업무관리시스템 API가 생기면 작업 프로세스에 예약 동기화를 추가한다.
- **나중:** 계정 신청 기능.

## 7. 데이터 흐름

```
[화면] ──엑셀 올리기──▶ [API 서버(FastAPI)] ──작업 등록──▶ [PostgreSQL] ◀──작업 처리── [작업 프로세스(Python)]
                                                         │                         │  (3단계) API 예약 동기화
                                                         │                         ▼
                                                         │                   업무관리시스템
                                                         ▼
                         일별 스냅샷 · 변동 기록 · 변동 구분 · 목표 설정 ──▶ 매출 페이지 블록들
```

- **API 서버(FastAPI)**는 화면 제공, 편집, 권한, 실시간 공동 편집, 업무 블록이 읽을 데이터 제공을 맡는다.
- **작업 프로세스(Python)**는 엑셀 읽기, API 동기화, 스냅샷 저장, 전일과 비교, 변동 자동 분류를 맡는다. API 서버와 같은 코드 저장소에 두고 DB 모델을 공유하되, 오래 걸리는 처리가 API 응답을 막지 않도록 프로세스를 나눈다. **[결정: Python / 제안: 프로세스 분리]**
- 두 프로세스는 **PostgreSQL을 통해 주고받는 것을 기본**으로 한다. **[제안]** 필요하면 **REST API로 서로 주고받아도 된다.** **[결정]** (8.8 참고)

### 7.1 일별 스냅샷 **[제안]**
- 날마다 본영업 영업 건 전체 값을 저장한다. 그래야 "기존 값", 증감액, 지난 날짜 화면을 만들 수 있다.
- 영업 건은 업무관리시스템의 고유번호로 구분한다(엑셀에도 있음). **[결정]**
- 지난 날짜 페이지는 그날 스냅샷으로 그린다. 나중에 원본이 바뀌어도 지난 페이지의 숫자는 바뀌지 않는다.
- **하루에 스냅샷 하나:** 그날 마지막으로 올리거나 동기화한 값이 그날 스냅샷이다. 같은 날 다시 올리면 덮어쓴다. (3단계 예약 동기화는 평일 업무 마감 무렵, 예: 18:00)
- **비교 대상:** 직전에 스냅샷이 있는 날(직전 기록일). 월요일은 금요일과 비교된다.

### 7.2 변동 구분 **[결정]**
- 기본 4개를 만들어 둔다: **목표매출 상향 · 신규매출 · 매출일정 앞당김 · 목표매출 제외**.
- 사람이 구분을 **추가·조회·수정·삭제**할 수 있다.
- 자동 분류 규칙 **[제안]**: 새로 생긴 건 → 신규매출, 금액 증가 → 목표매출 상향, 매출일정이 앞당겨짐 → 매출일정 앞당김, 확도가 바뀌어 목표에서 빠짐 → 목표매출 제외.
- **목표매출 제외 판단:** 지금은 확도가 바뀌는 것으로 판단한다. 노션 예시에서도 [고객] 건이 확도 중B → 하로 바뀌며 "목표매출 제외"로 올라 있다. 어느 확도부터 제외인지 정확한 기준은 **[확인 필요]** (사용자도 확인 필요하다고 함).
- 금액 감소, 일정 연기처럼 규칙에 안 맞는 변화는 "미분류"로 표시하고 사람이 구분을 고른다. **[제안]**

### 7.3 목표 금액 **[제안]**
- 연간·분기·월 목표는 새 시스템의 설정 화면에서 입력한다. API나 엑셀에 있으면 가져온다.

### 7.4 2단계: 엑셀 올리기 **[결정: 엑셀 가능 / 제안: 방식]**
- 업무관리시스템에서 엑셀을 내려받아 새 시스템 화면에 올린다(끌어다 놓기). API 서버는 파일을 저장하고 작업을 등록만 한다. 작업 프로세스가 읽어서 영업 건 고유번호로 전일 값과 맞춰 본다.
- 처리 결과(성공, 실패, 바뀐 건수)는 화면에 보여 준다.
- 영업 건 외에 영업활동, 일정, 계약·매출·수금도 엑셀로 받을 수 있는지는 **[확인 필요]**. 안 되면 해당 블록은 3단계(API)부터 채운다.

### 7.5 업무관리시스템에 요청할 API (요청서 초안) **[제안]**
읽기 전용. 날짜 범위로 조회할 수 있어야 한다.
1. **영업 건 목록** (본영업 Ent./Cloud): 고유번호(영업코드), 고객명, 제품, 사업 구분, 순매출/목표매출, 확도, 가중치, 단계, 매출 구분, 매출일정, 수금일, 계약예정일, 협력사/등급, 마지막 수정 시각
2. **영업활동 기록**: 일시, 영업코드, 고객, 제품, 주 내용, 연락 상대, 고객현황, 응대목표, 확도/단계, 영업관리 내용(본문)
3. **계약·매출·수금 실적과 예정**: 월별, 사업 구분별 금액과 건수, 고객별 내역
4. **일정**: 날짜, 시작·끝 시각, 내용, 담당자
5. (있으면) 연간·분기·월 목표 금액

| AFFiNE·AppFlowy·Docmost·Outline | 완성된 제품 | 업무 블록을 끼우기 어렵거나(구조가 크고 무거움), 데이터베이스가 없거나(Docmost·Outline), 라이선스 제약(AGPL·BSL) |

- R2까지 요구하는 한 litpage가 가장 짧은 길이다. 완성도가 최대 변수라 0단계 검증으로 확정한다. 실패하면 BlockNote + 직접 개발로 바꾸고 R2 범위를 줄인다.
- **메인 서버를 Python으로 정했으므로 litpage 서버(TypeScript, 약 4만 2천 줄)는 쓰지 않는다.** 가져오는 것은 화면(React)과 화면 쪽 공유 로직이다. 서버는 litpage 화면이 호출하는 API(`/api/rpc`) 규격에 맞춰 Python으로 새로 구현하고, 서버에서도 필요한 공유 로직(편집 연산 적용, 권한 확인, 동시 편집 병합)은 Python으로 옮긴다. 화면 쪽 TS 코드와 결과가 같아야 하므로 같은 입력·출력 테스트 케이스를 두 언어에서 함께 돌린다. **[제안]**

### 8.3 화면 — React + Vite + TypeScript **[결정]**

| 후보 | 장점 | 단점 |
|---|---|---|
| **React** | 에디터 선택지가 가장 많음(BlockNote는 React 전용, Lexical은 React 우선, Tiptap 지원). 표(TanStack Table)·차트 라이브러리와 자료가 가장 많음 | 상태 관리 방식이 다양해 처음에 규칙을 정해야 함 |
| Vue | 문법이 쉽고 구조가 일관됨 | BlockNote를 못 씀 → litpage 검증 실패 시 차선책도 막힘 |
| Svelte | 코드가 짧고 빠름 | 에디터·표 라이브러리가 적음 |
| Angular | 대규모 팀용 구조 | 5명 규모 내부 도구에 과함 |

- React는 litpage와 차선책(BlockNote)을 모두 열어 두는 유일한 선택이다.
- **빌드는 Vite:** Next.js의 강점(서버 렌더링, 검색 노출)은 로그인 뒤 사내 도구에 필요 없고, 서버가 Python이라 Next.js 서버 기능과 역할이 겹친다.

### 8.4 메인 서버 — Python + FastAPI **[결정]**

**언어** (숙련도는 근거에서 제외)

| 기준 | Python (FastAPI) | Go | Rust |
|---|---|---|---|
| 형식 없는 JSON 다루기(R5) | dict라 자연스러움. Pydantic으로 필요한 곳만 검증 | `map[string]any`와 타입 변환 반복, 장황함 | `serde_json::Value`로 안전하지만 코드가 가장 김 |
| litpage TS 서버 로직 이식 | 동적 타입이라 TS 구조와 가장 비슷, 이식이 가장 쉬움 | 구조체로 다시 설계 | 소유권 규칙 때문에 재설계, 가장 오래 걸림 |
| 화면과 API 타입 공유 | OpenAPI 자동 생성 → TS 타입 생성 | 별도 도구(huma, ogen 등) | 별도 도구(utoipa 등) |
| 동시 편집 생태계(Yjs 방식 전환 시) | pycrdt(yrs 바인딩) | 성숙한 구현 없음 | yrs |

| 정확성 보장 | 가장 약함 → Pydantic, mypy, 테스트로 보완 | 중간 | 가장 강함 |
| 배포 | 실행 환경 포함, 이미지가 큼 | 실행 파일 하나 | 실행 파일 하나, 빌드 느림 |
| 데이터 작업(R3)과 같은 언어 | 가능 → 백엔드 언어 하나 | — | — |

- Go·Rust가 앞서는 성능, 동시 접속, 배포 크기는 R4 규모에서 체감되지 않는다. 이 시스템의 핵심인 R5와 litpage 서버 이식에서는 Python이 가장 유리하다.
- Rust로 공유 로직을 짜서 화면에서도 WASM으로 쓰면 두 벌 관리를 없앨 수 있지만, 사실상 litpage를 다시 만드는 규모라 제외했다.

**프레임워크**

| 후보 | 장점 | 단점 |
|---|---|---|
| **FastAPI** | Pydantic 검증, OpenAPI 자동 생성, 비동기, WebSocket 내장, 생태계 가장 큼 | 구조(폴더·계층)를 직접 정해야 함 |
| Litestar | FastAPI와 비슷한 기능, 일부 성능·구조 기능이 더 있음 | 사용자·자료가 적음 |
| Django (+ Ninja/DRF) | 관리자 화면, 인증, ORM 내장 | 동기 중심 ORM, 무거움. litpage RPC 규격을 맞추는 데 내장 기능 대부분이 쓸모없음 |
| Flask | 단순함 | 비동기·검증·OpenAPI가 기본으로 없음 |

### 8.5 데이터 작업 — Python **[결정]**

| 기준 | Python | Go | Rust |
|---|---|---|---|
| 표끼리 비교·집계 | pandas·polars로 "영업코드로 합치고 열마다 비교"가 몇 줄 | 표 처리 라이브러리 미성숙, 직접 구현 | polars로 강력 |
| 엑셀 형식 | `.xlsx`(openpyxl), `.xls`(python-calamine) | excelize, `.xlsx`만 | calamine, 둘 다 |
| 규칙 변경 속도(변동 구분 규칙은 자주 바뀜) | 고치고 바로 실행 | 빠른 컴파일 | 컴파일 느림, 코드 김 |
| 데이터 형식 검증 | Pydantic·pandera로 보완 | 구조체로 강함 | 가장 강함 |
| 성능(하루 수백 건) | 차이 없음 | 차이 없음 | 차이 없음 |
| 메인 서버와 공유 | DB 모델(SQLAlchemy)·설정 공유 | — | — |

- 메인 서버와 같은 코드 저장소에 두고, 프로세스만 나눈다(API 서버 / 작업 프로세스). 엑셀 처리처럼 오래 걸리는 일이 API 응답을 막지 않게 하기 위해서다. **[제안]**
- **표 처리는 pandas [제안]:** 핵심 작업이 엑셀 읽기가 아니라 두 날짜의 표 비교라서 openpyxl 단독보다 pandas가 맞다(pandas도 `.xlsx`를 읽을 때 openpyxl을 씀). polars가 더 빠르지만 하루 수백 건에서는 차이가 없고, pandas가 자료와 SQLAlchemy 연동이 더 많다.
- **구형 `.xls` 대비:** 업무관리시스템 엑셀 형식을 모르므로 python-calamine을 함께 둔다. **[확인 필요: 엑셀 형식]**
- **행 검증:** 엑셀 한 행을 Pydantic 모델로 검증해, 열 이름이나 형식이 바뀌면 조용히 틀리지 않고 실패하게 한다. **[제안]**

### 8.6 DB — PostgreSQL **[결정]**

사용자 기준: "JSON을 다룰 필요가 있으면 PostgreSQL, 아니면 SQLite." litpage는 페이지·블록·데이터베이스 행을 모두 JSON으로 저장한다.

| 후보 | 결과 | 이유 |
|---|---|---|
| **PostgreSQL** | **선택** | JSONB 타입과 인덱스. API 서버와 작업 프로세스가 동시에 붙기 좋음. LISTEN/NOTIFY 내장. 백업 도구(pg_dump) 성숙 |
| SQLite | 제외 | 두 프로세스가 한 파일에 동시에 쓰기에는 잠금 제약. 사용자 기준에도 안 맞음 |
| MySQL·MariaDB | 제외 | JSON 인덱스 제약 등 JSON 지원이 약하고 장점이 없음 |

### 8.7 DB 접근과 구조 변경 관리 **[제안]**

| 영역 | 선택 | 비교한 대안과 이유 |
|---|---|---|
| DB 접근 | **SQLAlchemy 2.0 + psycopg 3** | psycopg 3은 동기·비동기를 모두 지원해 비동기 API 서버와 동기 작업 프로세스가 드라이버 하나를 함께 쓰고, LISTEN/NOTIFY도 지원함. asyncpg는 더 빠르지만 비동기 전용. SQLAlchemy는 pandas가 DB를 읽고 쓸 때 표준으로 받는 연결이고, 업무 테이블은 ORM 모델로, litpage식 JSON 레코드 저장은 Core(직접 SQL)로 나눠 쓸 수 있음. SQLModel은 FastAPI와 붙이기 쉽지만 SQLAlchemy 위의 얇은 층이라 고급 기능을 쓸 때 결국 SQLAlchemy로 내려와야 함. Tortoise·Peewee는 생태계가 작음 |
| 구조 변경 관리 | **Alembic** (이전 dbmate에서 변경) | dbmate를 골랐던 이유("두 언어가 같은 기준을 써야 함")가 백엔드가 Python 하나가 되면서 사라짐. Alembic은 SQLAlchemy 모델에서 변경 SQL 초안을 자동으로 만들어 줌. dbmate는 SQL을 전부 손으로 써야 하고, Flyway는 Java 실행 환경이 필요해 무거움 |

### 8.8 서비스 사이 주고받기 — DB 기본, REST 허용

| 후보 | 결과 | 이유 |
|---|---|---|
| **DB 작업 테이블 + LISTEN/NOTIFY** | **기본** **[제안]** | 이미 있는 PostgreSQL만으로 충분. 작업 기록이 남고, 작업 프로세스가 꺼져 있어도 작업이 사라지지 않음. 엑셀 처리·동기화처럼 오래 걸리고 다시 할 수 있어야 하는 작업에 맞음 |
| **REST API** | **허용** **[결정]** | 바로 답이 필요한 요청(엑셀 미리보기, 동기화 상태 조회, 수동 재처리)에 맞음. 사내망 안에서만 열고 서비스 간 토큰으로 막음 **[제안]** |
| Redis + 큐(Celery, RQ, Dramatiq) | 제외 | 하루 몇 건 작업에 서버 하나를 더 운영해야 함 |

- 오래 걸리거나 실패 시 다시 해야 하는 작업은 DB 작업 테이블, 바로 답이 필요한 조회는 REST. 세부는 개발자가 정한다.

### 8.9 세부 도구 **[제안]**

| 영역 | 선택 | 비교한 대안과 이유 |
|---|---|---|
| 예약 실행 | **APScheduler** | 매일 18시 실행 + 수동 실행 버튼 필요. cron은 컨테이너 밖에 설정이 흩어지고 상태를 화면에서 보기 어려움. Celery beat는 메시지 큐 서버가 필요함. pg_cron은 SQL만 실행해 Python 작업을 못 돌림 |
| Python 패키지 관리 | **uv** | pip는 잠금 파일이 없어 서버마다 버전이 달라질 수 있음. Poetry는 느림. conda는 무거움. uv는 잠금 파일, Python 버전 관리, 속도를 모두 갖춤 |
| API 타입 공유 | **FastAPI OpenAPI → openapi-typescript** | 서버의 Pydantic 모델에서 화면용 TS 타입을 생성해, 주소·형식이 어긋나면 화면 빌드에서 바로 걸림. 손으로 타입을 맞추는 방식은 어긋나도 실행해야 알 수 있음. litpage 화면이 쓰는 기존 RPC는 litpage의 TS 타입을 기준으로 맞춤 |
| 차트 | **ECharts** | Recharts는 React에 붙이기 쉽지만 세부 조정이 제한적. Chart.js는 차트 종류가 적음. Nivo는 무거움. ECharts는 누적 막대·상세 툴팁이 강하고 캘린더 히트맵을 기본 제공해 첫 화면 캘린더에 바로 쓸 수 있음 |
| 서버 실행 | **uvicorn** | FastAPI 표준 실행기. 5명 규모라 gunicorn 다중 작업자 구성은 필요 없음 |
| 정적 파일(화면) 제공 | **FastAPI가 직접 제공** | nginx·Caddy를 앞에 두면 컨테이너가 하나 늘어남. 5명 규모에서는 이득이 없음. HTTPS가 필요해지면 그때 Caddy 추가 |

### 8.10 로그인

| 후보 | 장점 | 단점 |
|---|---|---|
| **자체 계정(관리자 발급)** | 5명 규모에 가장 단순 | 비밀번호를 직접 관리 |
| fastapi-users 등 인증 라이브러리 | 가입·재설정 흐름 제공 | 회원가입을 쓰지 않아 대부분 불필요 |
| Keycloak·Authentik | 사내 여러 시스템 로그인 통합 | 서버를 하나 더 운영 |
| 회사 AD·LDAP 연동 | 회사 계정 그대로 사용 | 회사에 AD가 있는지 모름 |

- 관리자가 계정을 만들고, 회원가입은 두지 않는다. 계정 신청 기능은 보류. **[결정]**
- 비밀번호는 argon2로 해시한다(bcrypt보다 최신 권장 방식). 로그인 상태는 HttpOnly 세션 쿠키로 유지한다. 같은 도메인의 웹 화면만 쓰므로 JWT보다 단순하고, 서버에서 바로 로그아웃시킬 수 있다. **[제안]**
- 회사에 AD가 있으면 나중에 LDAP 연동으로 바꾼다. **[확인 필요]**

### 8.11 배포 — 사내 서버 + Docker Compose

| 후보 | 장점 | 단점 |
|---|---|---|
| **Docker Compose** | API 서버·작업 프로세스·PostgreSQL을 설정 파일 하나로 띄우고 버전 고정. 업데이트 실패 시 이전 이미지로 되돌리기 쉬움 | Docker를 알아야 함 |
| 직접 설치(systemd) | 구조가 단순 | Python·PostgreSQL 버전을 서버에서 직접 관리. 서버를 바꾸면 처음부터 다시 맞춰야 함 |
| Kubernetes | 확장성 | 서버 한 대 규모에 과함 |

- 사내 서버 설치 **[결정]**, Docker Compose **[제안]**.
- **백업:** 매일 pg_dump로 DB를 파일로 남기고 업로드 파일 폴더와 함께 보관. **[제안]**
- **사내 서버가 Windows라면** Docker 운영에 WSL2가 필요해 번거로워진다. 운영체제를 먼저 확인한다. **[확인 필요]**

# 일일보고 대시보드 설계 — 노션 이관 (2026-11-25)

> 상태: 사용자 승인 (2026-11-25). 회사 내부 승인(기획안)은 아직 전
> 표기: **[결정]** 사용자가 정한 것 · **[제안]** 에이전트가 정한 것(사용자가 바꿀 수 있음) · **[확인 필요]** 아직 모르는 것

## 1. 배경과 목적

- 회사는 노션 초창기부터 노션을 써 왔다. 자율성이 높고 마크다운이라 작성이 편해서다.
- 개인별 업무목록, 제품별 QA목록 등 여러 페이지를 시도했지만 대부분 정착하지 못했다. 지금 실제로 쓰는 것은 두 페이지뿐이다.
  - **일일 업무보고** (예: `[담당자] 실장 업무보고 - 2026년 11월24일(화)`)
  - **본영업 목표매출 관리 현황** (예: `본영업 목표매출 관리 현황 - 2026년 11월 23일(월)`)
- 이 두 페이지를 노션이 아닌 자체 시스템으로 옮기라는 지시가 있었다. **[결정]**
- 이관 이유:
  1. **비용 절감** — 노션 비용은 월 5만 원 정도. 가장 큰 이유. (이관할 가치가 있는지의 판단은 이번 기획 범위가 아님) **[결정]**
  2. **막막함 해소** — 노션은 자율성이 너무 높아서 무엇을 어떻게 만들지 막막하다. 그래서 범용 기능 위에 **업무관리에 특화된 컴포넌트**(예: 매출관리 전용 컴포넌트)를 갖춘 "업무관리 특화 노션"을 만든다. **[결정]**
- 노션의 기본 기능(범용 데이터베이스 포함)은 웬만하면 모두 넣는다. **[결정]**
- 지금 매출 페이지의 숫자는 기존 **업무관리시스템**(사내 웹 시스템)에 있는 값을 사람이 노션으로 옮겨 적고 있다. 업무관리시스템은 엑셀 내려받기가 되고(영업 건마다 고유번호 있음), API는 "제공할 수 있다"는 말까지만 들었다. **[결정]**

## 2. 목표 · 비목표 · 실패 기준

### 목표
- 노션의 기본 기능(페이지, 블록 에디터, 데이터베이스와 여러 보기 등)을 갖춘 사내 워크스페이스. **[결정]**
- 그 위에 업무 전용 화면 3개: 캘린더 → 그날의 일일 업무보고 / 본영업 목표매출 관리 현황. **[결정]**
- 매출 페이지는 사람이 옮겨 적지 않는다. 업무관리시스템 데이터(처음엔 엑셀, 나중엔 API)로 채워진다.
- 날마다 기록이 남는다. 지난 날짜를 열면 그날 상태를 그대로 볼 수 있다. **[결정]**
- 지난 페이지도 고칠 수 있고, 고친 기록(누가, 언제, 무엇을)이 남는다. **[결정]**
- PC 화면 기준으로 만들되 모바일에서도 보기 좋게(반응형) 만든다. **[결정]**
- 직접 쓰는 부분은 노션처럼 마크다운으로 편하게 쓴다. 업무 페이지는 빈 화면이 아니라 틀로 시작한다.

### 비목표 (이번에 하지 않음)
- 정착하지 못한 다른 노션 페이지(개인 업무목록, QA목록 등)의 이관. 범용 기능이 있으니 필요하면 사용자가 직접 만들 수 있다.
- 업무관리시스템에 값을 되돌려 쓰기 (읽기만 함) **[제안]**
- 모바일 전용 앱 (반응형 웹으로 대신함) **[결정]**
- 계정 신청 기능 (나중에 처리, 지금은 보류) **[결정]**
- litpage 원본 저장소의 업데이트 따라가기 (코드를 가져온 뒤에는 독립적으로 관리) **[결정]**
- 노션 → 새 시스템 과거 데이터 일괄 이전 **[제안, 확인 필요]**

### 실패 기준 (기술적으로 동작해도 실패로 보는 것)
- 노션보다 쓰기 불편하다.
- 여전히 누군가 매출 숫자를 손으로 옮겨 적어야 한다 (엑셀 올리기 한 번은 허용, API가 생긴 뒤에는 그것도 없어야 함).
- 다시 "무엇을 써야 할지 막막한" 상태가 된다.

### 범용 기능과 "막막함"의 균형 **[제안]**
범용 데이터베이스까지 넣으면 노션처럼 다시 막막해질 위험이 있다. 그래서:
- 로그인하면 **캘린더(업무 화면)**가 첫 화면이다. 빈 워크스페이스가 아니다.
- 업무 페이지는 정해진 틀과 전용 블록으로 시작한다.
- 범용 페이지·데이터베이스는 사이드바의 별도 영역에서 쓴다. 업무 화면을 쓰는 데 범용 기능을 알 필요가 없다.

## 4. 구현 방식

### 4.1 큰 방향
세 가지를 검토했고, 사용자는 **B. 업무 전용 블록이 있는 노션형 에디터**를 골랐다. **[결정]**

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 고정 틀 + 마크다운 입력칸 | 칸 고정, 글은 마크다운 칸, 매출은 자동 | 가장 빠르고 싸다 | 칸 변경에 개발자 필요. 노션 같은 작성감 없음 |
| **B. 업무 전용 블록이 있는 노션형 에디터 (선택)** | 노션처럼 쓰다가 `/`로 블록 삽입, 업무 전용 블록 제공, 틀로 시작 | "업무관리 특화 노션"에 가장 가깝다 | A보다 개발이 크다 |
| C. 오픈소스 노션 대체재 설치만 | 노션 비슷한 프로그램 설치 + 데이터 넣는 프로그램 | 에디터를 거의 공짜로 얻음 | 계산하는 전용 블록이 어렵고, 막막함이 그대로 |

### 4.2 출발점: litpage 코드를 가져와 고쳐 쓴다 **[결정]**
사용자 요청에 따라 [litpage](https://github.com/litmers-dev/litpage)를 BlockNote와 비교했고, **litpage**로 정했다.

- **포크하지 않는다.** litpage 코드를 이 저장소로 가져와 독립적으로 고친다. 원본과 연결하지 않고 업데이트도 따라가지 않는다. MIT 라이선스이므로 원본 저작권 고지(`LICENSE`, `THIRD_PARTY_NOTICES.md`)는 남긴다. **[결정]**
- **기술은 그대로 따르지 않는다.** litpage 시스템을 참고하되, 기술 스택은 이 시스템에 맞게 다시 고른다(8장). **[결정]**
- 노션식 `/` 메뉴, 마크다운 단축키, 사용자 정의 블록은 유지한다. **[결정]**

**litpage를 살펴본 결과** (2026-11-25, 저장소 `f55fead` 기준)
- 에디터 라이브러리가 아니라 **노션 같은 워크스페이스 전체**다. 블록 에디터(41종 블록, `/` 메뉴, 마크다운 단축키, 끌어서 옮기기, 멘션, 댓글, 제안 편집, 버전 기록), 데이터베이스(표·보드·목록·갤러리·캘린더·타임라인·차트·대시보드·피드·폼·지도 보기, 수식, 관계, 롤업, 자동화), 권한, 실시간 공동 편집, REST API·웹훅이 들어 있다. 한국어 화면을 지원한다.
- 구성: React 19 + Vite(화면), Node.js 26 + Hono(서버), SQLite 파일 하나(저장), WebSocket(실시간). 에디터는 외부 라이브러리 없이 직접 만들었다. 블록은 `registerBlock`, 데이터베이스 보기는 `registerView`로 추가한다.
- 코드 규모: 서버 약 4만 2천 줄, 화면 약 9만 3천 줄, 화면·서버 공유 로직(`packages/shared`: 레코드, 편집 연산, 권한, 수식 엔진, 동시 편집 병합) 약 1만 6천 줄.
- **주의할 점:** 2026-10-23 첫 공개, 커밋 8개, 버전 0.1.0. AI 코딩 에이전트가 약 21시간 만에 만든 실험 프로젝트로, 저장소 스스로 "연구·시연용, 있는 그대로 제공"이라고 밝힌다. 그래서 본격 개발 전에 검증한다(6.2 0단계).

**BlockNote와 비교** (참고용)

| 기준 | litpage 가져오기 (선택) | BlockNote로 직접 개발 |
|---|---|---|
| 노션 기본 기능(데이터베이스·보기·권한·버전 기록·댓글) | 이미 있음 | 전부 새로 만들어야 함. 데이터베이스와 보기만 해도 수개월 |
| 업무 전용 블록 | `registerBlock`으로 추가 | 사용자 정의 블록 API로 추가 |
| 에디터 성숙도 | 자체 에디터, 검증 기간 짧음 | ProseMirror/Tiptap 기반, 여러 해 쓰인 라이브러리 |

0단계 검증에서 litpage가 기준을 못 넘으면 BlockNote로 바꾼다. 그때 바뀌는 것은 에디터와 범용 기능을 직접 만드는 부분뿐이고, 8장의 나머지 기술 선택은 그대로 쓴다.

## 5. 화면 구성 — 업무 화면 3개 **[결정]**

```
첫 화면: 1depth 캘린더 ──날짜 클릭──▶ 2depth 일일 업무보고 (그날)
                                 └──▶ 2depth 본영업 목표매출 관리 현황 (그날)
사이드바: 범용 페이지·데이터베이스 영역 (노션 기본 기능)
```

### 5.1 캘린더 (1depth)
- 월 단위 달력. 날짜를 누르면 그날의 두 페이지로 들어간다.
- 날짜 칸에 보여 줄 것 **[제안]**: 업무보고·매출 페이지 작성 여부, 그날 매출 증감액(예: `+22,427,592 ▲`)
- 오늘 날짜로 바로 가는 버튼.

### 5.2 일일 업무보고 (2depth)
노션 원본 구성: 인사 관리 → 주요보고 & 오늘 업무(주요 보고, 오전, 오후).

| 영역 | 데이터 출처 | 블록 |
|---|---|---|
| 인사 관리 (구인 사이트, 직군별 채용 현황, 지원자 수) | **직접 입력** — 업무관리시스템에 없음 **[결정]** | 채용 현황 블록 |
| 주요 보고 | **직접 작성** (마크다운) **[결정]** | 기본 글 블록 |
| 오늘 일정 (오전/오후 시간대별) | **업무관리시스템에서 가져옴** **[결정]** | 일정 블록 |

- 새 날짜 페이지는 틀로 시작하고, 직접 입력하는 블록(채용 현황, 주요 보고)은 직전 작성일 페이지의 최신 내용을 이어받는다. **[제안]**
- 일정 블록은 가져온 일정을 보여 주되, 사람이 항목을 추가·수정할 수 있다. **[제안]**
- 페이지는 "날짜 + 작성자"로 저장한다. 지금은 작성자가 한 명이라 한 페이지만 보이고, 사람이 늘어도 구조를 다시 짜지 않는다. 일정은 작성자(담당자) 기준으로 가져온다. **[제안]**

### 5.3 지난 페이지 수정과 기록 **[결정]**
- 지난 날짜 페이지도 고칠 수 있다(직접 쓴 글, 채용 현황, 변동 구분).
- 고칠 때마다 기록을 남긴다: 누가, 언제, 무엇을 바꿨는지. 이전 버전을 열어 볼 수 있다. (litpage 버전 기록 기능 활용)
- 업무관리시스템에서 온 숫자(변동사항, 매출 요약, 계약·매출·수금, 영업활동, 일정 원본)는 그날 스냅샷으로 고정된다. **[제안]**
- "확정"이나 잠금 기능은 두지 않는다. 노션에도 없던 절차를 늘리지 않기 위해서다. **[제안]**

### 5.4 본영업 목표매출 관리 현황 (2depth)
노션 원본 구성: 접힌 섹션(매출 현황, 영업활동 관리, 일별 현황) → 2026년 본영업 매출 요약 → 변동사항 표 → 관리 매출 현황.

- **대상:** 본영업 두 가지(본영업 Ent., 본영업 Cloud) 영업 건만 올라간다. **[결정]**

| 영역 | 데이터 출처 | 블록 |
|---|---|---|
| 매출 요약: 오늘 증감액, 목표 매출, 목표 대비 예상(%), 4분기 목표/현황, 이번 달 목표/현황 (▲▼ 증감) | 목표 금액은 설정값, 현황은 자동 계산 | 매출 요약 블록 |
| 변동사항 표: 고객명, 구분, 제품, 순매출, 증감액, 확도, 가중치, 매출 구분, 매출일정 (바뀌기 전 값은 "기존: …"으로 함께 표시) | 자동 생성 (그날 스냅샷을 직전 기록일과 비교) | 변동사항 블록 |
| 계약·매출·수금 현황: 이번 달 완료/예정을 3단계 막대그래프로, 본영업 Ent./Cloud별 건수·금액 | 업무관리시스템 | 계약·매출·수금 블록 |
| 영업활동 기록: 고객별 카드(시각, 고객, 제품, 주 내용, 연락 상대, 확도/단계, 협력사, 매출일/수금일, 목표매출, 영업관리 내용) | 업무관리시스템 | 영업활동 블록 |
| 메모 | 직접 작성 | 기본 글 블록 |

- 접힌 섹션 3개의 정확한 내용은 사용자도 모른다. 업무관리시스템 화면(계약·매출·수금 그래프, 영업활동 카드)과 비슷한 내용으로 추정한다. **[확인 필요]**
- 블록은 접기/펼치기가 된다. **[제안]**
- 사장님이 모니터에 띄워 보시므로, 숫자와 그래프가 멀리서도 읽히는 크기로 만든다. **[제안]**

### 5.5 숫자 규칙
- **변동사항 표의 "기존"**: 바뀌기 전 값. 예: 목표매출 상향 시 `기존 [금액] → [금액], 증감 [금액] ▲`. **[결정]**
- **오늘 증감액**: 그날 스냅샷을 직전 기록일 스냅샷과 비교해 생긴 변동의 증감액 합. **[제안]**
- **목표 대비 예상**: 가중치를 곱한 값이 아니라 절대 금액 기준. **[결정]** 정확한 계산식(어떤 건을 더하는지)은 **[확인 필요]**.
- **확도와 가중치**: 서로 다른 지표다. 지금은 화면에 보여 주기만 하고 계산에 쓰지 않는다. **[결정]**
- **증감액의 기준 금액**: 순매출로 본다. **[제안, 확인 필요]**

### 7.1 일별 스냅샷 **[제안]**
- 날마다 본영업 영업 건 전체 값을 저장한다. 그래야 "기존 값", 증감액, 지난 날짜 화면을 만들 수 있다.
- 영업 건은 업무관리시스템의 고유번호로 구분한다(엑셀에도 있음). **[결정]**
- 지난 날짜 페이지는 그날 스냅샷으로 그린다. 나중에 원본이 바뀌어도 지난 페이지의 숫자는 바뀌지 않는다.
- **하루에 스냅샷 하나:** 그날 마지막으로 올리거나 동기화한 값이 그날 스냅샷이다. 같은 날 다시 올리면 덮어쓴다. (3단계 예약 동기화는 평일 업무 마감 무렵, 예: 18:00)
- **비교 대상:** 직전에 스냅샷이 있는 날(직전 기록일). 월요일은 금요일과 비교된다.

### 7.2 변동 구분 **[결정]**
- 기본 4개를 만들어 둔다: **목표매출 상향 · 신규매출 · 매출일정 앞당김 · 목표매출 제외**.

- 자동 분류 규칙 **[제안]**: 새로 생긴 건 → 신규매출, 금액 증가 → 목표매출 상향, 매출일정이 앞당겨짐 → 매출일정 앞당김, 확도가 바뀌어 목표에서 빠짐 → 목표매출 제외.
- **목표매출 제외 판단:** 지금은 확도가 바뀌는 것으로 판단한다. 노션 예시에서도 [고객] 건이 확도 중B → 하로 바뀌며 "목표매출 제외"로 올라 있다. 어느 확도부터 제외인지 정확한 기준은 **[확인 필요]** (사용자도 확인 필요하다고 함).

### 8.2 메인 서버 언어 — TypeScript **[결정]**

litpage는 편집 연산, 권한, 수식 엔진, 동시 편집 병합 같은 핵심 로직을 화면과 서버가 **같은 코드로** 함께 쓴다(서버 115개 파일, 화면 305개 파일이 가져다 씀). 서버만 다른 언어로 바꾸면 이 로직을 그 언어로 다시 만들고, 앞으로 고칠 때마다 두 언어의 결과를 똑같이 맞춰야 한다. 동시 편집 병합은 결과가 조금만 달라도 글이 깨진다.

| 후보 | 결과 | 이유 |
|---|---|---|
| **TypeScript (Node.js)** | **선택** | 핵심 로직을 한 벌로 유지 (0순위) |
| Python (FastAPI 등) | 메인 서버로는 제외 | 익숙하지만 핵심 로직 이중 관리. 대신 작업 서비스에 사용 |
| Go | 제외 | 동시 접속 처리·배포(실행 파일 하나)는 좋지만, 5명 규모에서 성능 이점이 의미 없고 이중 관리 부담은 같음 |
| Rust | 제외 | 핵심 로직을 Rust로 만들어 화면에서도(WASM) 쓰게 할 수는 있으나 사실상 litpage를 처음부터 다시 만드는 일이고 개발 속도가 가장 느림 |

**서버 프레임워크 — Hono 유지 [제안]:** 가볍고 타입 지원이 좋다. litpage에서 Hono는 4개 파일에서만 쓰여 바꾸기 쉽지만, Fastify·Express로 바꿔서 얻는 기능상 이득이 없다. NestJS는 구조가 무거워 이 규모에 과하다.

**Node.js 버전:** litpage는 Node.js 26 이상을 요구한다(TypeScript 파일을 바로 실행). 2026년 10월 LTS가 된 버전이라 그대로 쓴다. SQLite를 걷어내면 `node:sqlite` 의존은 사라진다.

### 8.3 작업 서비스 — Python **[결정]**

| 후보 | 결과 | 이유 |
|---|---|---|
| **Python 별도 서비스** | **선택** | 엑셀 읽기, 비교, 분류 같은 데이터 처리는 Python이 강하고, 업무 규칙이 가장 자주 바뀌는 곳이라 관리자가 익숙한 언어로 두는 것이 맞음 (0순위에서 TS와 비슷, 1·2순위에서 Python이 앞섬) |
| TypeScript로 메인 서버 안에 | 대안 | 언어·실행 환경이 하나라 관리가 가장 단순. 대신 업무 규칙을 고칠 때 TypeScript를 다뤄야 함 |

세부 선택 **[제안]**:
- **엑셀 읽기: openpyxl** — xlsx를 직접 읽는 표준 라이브러리. pandas는 표 계산에 강하지만 이 정도 비교에는 무겁고 의존성이 크다.
- **DB 접근: psycopg 3** — PostgreSQL 공식 계열 드라이버, LISTEN/NOTIFY 지원. SQLAlchemy ORM은 테이블 몇 개에 과하고, asyncpg는 비동기가 필요 없는 작업에 복잡도만 더한다.
- **예약 실행: APScheduler** — 하루 한 번 작업을 서비스 안에서 돌린다. OS cron은 컨테이너 밖 설정이 하나 늘고, Celery는 Redis 등 메시지 큐가 필요해 과하다.
- **패키지 관리: uv** — 빠르고 잠금 파일로 같은 환경을 재현한다. pip+requirements.txt는 잠금이 약하고, Poetry보다 설치·실행이 빠르다.
- **버전:** Python 3.13 이상.

### 8.4 DB — PostgreSQL **[결정]**

사용자 기준: "JSON을 다룰 필요가 있으면 PostgreSQL, 아니면 SQLite." litpage는 페이지·블록·데이터베이스 행을 모두 JSON으로 저장한다(SQL 안 JSON 함수 68곳, 서버의 JSON 변환 120곳). 그래서 PostgreSQL로 간다.

| 후보 | 결과 | 이유 |
|---|---|---|
| **PostgreSQL** | **선택** | JSONB 타입과 인덱스로 JSON 조회가 빠름. TS 서버와 Python 서비스가 동시에 붙기 좋음. 백업 도구(pg_dump) 성숙 |
| SQLite | 제외 | JSON 함수는 있지만 두 서비스가 한 파일에 동시에 쓰기에는 잠금 제약이 있음. 사용자 기준에도 맞지 않음 |
| MySQL·MariaDB | 제외 | JSON 지원이 PostgreSQL보다 약하고(JSON 인덱스 제약) 장점이 없음 |

- **전환 비용:** litpage 서버는 SQLite 동기식 API를 65개 파일, 455곳에서 쓴다. 이를 비동기로 바꾸는 것이 1단계의 핵심 작업이다.
- **TS 쪽 접근: node-postgres(`pg`) + 얇은 변환층 [제안]** — litpage의 `prepare(sql).get/all/run(?…)` 형태를 그대로 받아 `$1…` 형태로 바꿔 주는 층을 두면, 455곳의 SQL 문장을 대부분 그대로 살리고 `await`만 붙이면 된다. postgres.js는 빠르지만 템플릿 문자열 방식이라 문장을 하나하나 다시 써야 하고, Drizzle·Prisma 같은 ORM은 기존 SQL을 전부 새 문법으로 옮겨야 한다.
- **DB 구조 변경 관리: dbmate [제안]** — SQL 파일로 변경 이력을 관리하는 언어 무관 도구라 TS와 Python이 같은 기준을 쓴다. Alembic은 Python 전용, Drizzle Kit·Prisma Migrate는 TS 전용이라 한쪽 언어에 묶인다.

### 8.5 서비스 사이 주고받기 — PostgreSQL 기본, REST API 허용

| 후보 | 결과 | 이유 |
|---|---|---|
| **DB 작업 테이블 + LISTEN/NOTIFY** | **기본** **[제안]** | 이미 있는 PostgreSQL만으로 충분. 작업 기록이 남고, 서비스가 꺼져 있어도 작업이 사라지지 않음. 엑셀 처리·동기화처럼 시간이 걸리고 결과를 나중에 봐도 되는 작업에 맞음 |
| **REST API (Python 서비스에 FastAPI 등)** | **허용** **[결정]** | 바로 답이 필요한 요청(예: 엑셀 미리보기, 동기화 상태 조회, 수동 재처리)에 맞음. 서비스 사이 호출 경로와 인증이 하나 더 생기므로 사내망 안에서만 열고 서비스 간 토큰으로 막음 **[제안]** |
| Redis + 큐(Celery, RQ) | 제외 | 하루 몇 건 작업에 서버 하나를 더 운영해야 함 |

- 어떤 기능을 DB로, 어떤 기능을 REST로 주고받을지는 개발자가 정한다. 기준: 오래 걸리거나 실패 시 다시 해야 하는 작업은 DB 작업 테이블, 바로 답이 필요한 조회는 REST.

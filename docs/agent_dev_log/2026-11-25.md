### 기획 대화에서 확인된 내용
- **이관 이유:** 가장 큰 이유는 노션 비용 절감
- **노션 사용 이력:** 자율성이 높고 마크다운이라 작성이 편해서 노션 초창기부터 도입함. 사이드바의 여러 페이지(개인별 업무목록, QA목록 등)를 시도했지만 모두 정착하지 못했고, 지금은 화면 속 두 페이지(일일 업무보고, 본영업 목표매출 관리 현황)만 실제로 쓰고 있음
- **에이전트 판단(제안, 일부 수정됨):** 처음에는 이관 범위를 실제로 쓰는 두 페이지로 한정하자고 제안했으나, 아래 사용자 답변으로 범위가 바뀜. 노션의 장점(자유로운 작성, 마크다운)을 잃으면 실패로 본다는 기준은 유지
- **사용자 규모와 비용:** 매일 작성하는 사람 약 4명 + 보고받는 사장님 1명. 노션 비용은 월 5만 원 정도
- **이관 가치 판단은 보류:** 사용자가 판단할 사항이 아니므로 비용 비교는 일단 제쳐두고 이관 설계부터 진행하기로 함
- **옮길 범위(사용자 결정):** 두 페이지를 그대로 복제하는 것이 아니라 "업무관리에 특화된 노션"을 만든다. 예: 노션의 범용 데이터베이스 대신 매출관리에 특화된 컴포넌트
  - 이유: 노션은 자율성이 너무 높아서 오히려 무엇을 어떻게 만들지 막막함. 여러 페이지를 시도했다가 정착하지 못한 원인으로 보임
- **에이전트 해석(제안):** 자유롭게 쓰는 문서(마크다운) 위에, 업무용으로 미리 만들어 둔 블록(매출 현황, 채용 현황, 하루 일정 등)과 역할별 기본 틀을 얹는 방향. 빈 페이지에서 시작하지 않게 하는 것이 핵심

- **사용자 규모 정정:** "4명이 매일 쓴다"는 말은 정확하지 않았음. 실제로는 화면 속 두 페이지만 쓰이고 있고, 그래서 비용도 월 5만 원 정도에 그침
- **범위 확정(사용자 결정):** 실제로 쓰는 페이지만 만든다. 화면 구성은 총 3개
  - 1depth: 캘린더 같은 화면 (날짜를 고르는 입구)
  - 2depth: 그날의 일일 업무보고 페이지, 그날의 본영업 목표매출 관리 현황 페이지
  - 앞서 정한 "업무관리 특화" 방향(범용 데이터베이스 대신 매출관리 전용 컴포넌트 등)은 이 두 페이지 안에서 적용

### 남은 일 / 다음 작업
- 브라우저 화면 시안을 제안했으나, 사용자가 "지금 단계에서 중요한가?"라고 물음 → 에이전트도 지금은 아니라고 판단. 화면 배치보다 각 페이지에 무엇이 들어가고 날짜마다 데이터가 어떻게 이어지는지가 먼저. 시안은 구조가 정해진 뒤로 미룸
- 다음 질문: 매일 페이지를 새로 쓰는지 전날 것을 이어받는지, 매출 표의 "기준" 값이 무엇을 뜻하는지
- **"기준"이 아니라 "기존"(사용자 정정):** 매출 표는 변동사항을 기록하는 노션 DB임. 예: 목표매출 상향이면 "기존 [금액] → [금액], 증감 [금액]▲"처럼 기존 값 대비 얼마나 바뀌었는지 적음. 표의 "구분" 값(목표매출 상향, 신규매출, 매출일정 앞당김, 목표매출 제외)이 변동 종류임
- **날마다 기록은 남겨야 함(사용자 결정)**
- **에이전트 해석(제안):** 고객별 매출 건을 한 벌의 데이터로 관리하고, 값을 고칠 때마다 "변동 기록"(종류, 기존 값 → 새 값, 날짜)이 자동으로 쌓이게 함. 날짜 페이지는 그날의 변동 기록과 그 시점 합계를 보여 줌. 확도→가중치는 매우높음=High(100%), 하=Low(10%)처럼 연결되고, 목표 대비 예상은 순매출×가중치 합으로 추정(미검증)
- 노션 커넥터로 원본 페이지를 찾아봤으나, 연결된 계정은 개인 워크스페이스라 회사 페이지(게스트로 참여 중)는 검색되지 않음. 화면 캡처 기준으로 진행
- 다음 질문: 매출 페이지에서 접혀 있는 "매출 현황", "영업활동 관리", "일별 현황"에 무엇이 들어 있는지
- **사용자 정정:**
  - 확도와 가중치는 서로 다른 지표임. 지금 단계에서는 중요하지 않으니 알고만 있기로 함(에이전트의 "확도→가중치 연결" 추정은 틀림)
  - "목표 대비 예상"은 가중치를 곱한 값이 아니라 절대적인 증감량임
- **접힌 섹션 내용:** 사용자도 정확히는 모르지만, 아래 두 화면과 비슷한 내용으로 추정
  - 영업활동 기록 카드: 시각(오후 4:45), 고객([고객]), 제품([제품] 이전설치 1식), 주 내용(신규문의), 메일(수신) 상대, 고객현황, 응대목표, 확도/단계(상A ▶ 상A / 58 / 영업개시 / 일반), 협력사/등급(직판, 중립), 매출/수금일(12-18(4Q) / 2027-01-29(1Q)), 목표매출([금액]), 영업관리 내용(자유 서술 글머리표), 접기 버튼

- 다음 질문: 두 화면의 출처(기존 사내 시스템인지)와 노션 매출 페이지와의 관계

- **에이전트 제안:**
  - 매출 페이지는 손으로 옮겨 적지 않고 API로 가져와 자동으로 만든다. 노션 대비 가장 큰 이점
  - 업무관리시스템은 읽기만 하고, 새 시스템에서 되돌려 쓰지 않는다
  - API가 현재 값만 주는 경우를 대비해 새 시스템이 매일 그 시점 값을 저장(스냅샷)하고, 전날과 비교해 변동 기록과 증감액을 계산한다
  - 변동 "구분"은 규칙으로 자동 분류할 수 있는지 검토(새 건→신규매출, 금액 증가→목표매출 상향, 일정 당김→매출일정 앞당김, 빠진 건→목표매출 제외). 사람이 고칠 수 있게 둠
  - 연간·분기·월 목표 금액은 업무관리시스템에 없을 가능성이 있어 새 시스템에서 설정값으로 입력
- 다음 질문: 일일 업무보고의 일정·주요 보고가 업무관리시스템에도 있는지, 노션에서만 쓰는지
- **사용자 결정:**
  - 변동 구분: 기본으로 4개(목표매출 상향, 신규매출, 매출일정 앞당김, 목표매출 제외)를 만들어 두고, 사람이 추가·조회·수정·삭제할 수 있게 함
  - API: 아직 없음. "제공 가능하다"는 말까지만 들은 상태 → 새 시스템에 필요한 API 요구사항을 기획서에 정리해 업무관리시스템 쪽에 요청해야 함. API가 생기기 전까지 쓸 임시 방법도 필요

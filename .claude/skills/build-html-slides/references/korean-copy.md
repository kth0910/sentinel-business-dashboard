# 한국어 발표 문장

한국어 슬라이드, 발표자 노트, 슬라이드 상세 해설을 만들 때 읽는다. 아래 원칙은 [epoko77-ai/im-not-ai](https://github.com/epoko77-ai/im-not-ai)의 공개 규칙에서 발표 자료에 맞는 항목을 추려 적용한 것이다.

## 이름과 언어

- 공식 한국어 이름이 확인되면 한국어를 기본 표기로 쓴다. 원어는 첫 등장에만 작게 병기한다.
- 공식 한국어 이름이 없으면 고유명사를 멋대로 번역하지 않는다. 자연스러운 음역 또는 원어를 쓰고, 청중이 이해해야 하는 설명만 한국어로 덧붙인다.
- 영어 키커와 영어 카드 제목은 장식이 아니라 정보일 때만 쓴다. 한국어로 충분하면 한국어를 쓴다.
- 업계 표준 약어, 규격, 모델명, 수치, 날짜는 보존한다.

## 문장

- 발표자가 입으로 말할 법한 짧고 구체적인 문장을 쓴다.
- “~를 통해”, “~에 있어서”, “~에 기반하여”, “가지고 있다”를 습관처럼 쓰지 않는다. 조사나 동사로 바로 연결한다.
- “결론적으로”, “주목할 만하다”, “시사하는 바가 크다”, “본질적으로”, “지금이야말로” 같은 상투어를 피한다.
- “첫째·둘째·셋째”식 기계적 병렬과 똑같은 세 카드 구성을 반복하지 않는다.
- “또한·따라서·즉·나아가”로 문장을 연달아 시작하지 않는다.
- 명사형 표현을 동사로 풀고, 피동보다 능동을 우선한다.
- 같은 길이와 같은 종결어미가 네 문장 이상 이어지지 않게 리듬을 섞는다.
- 과장 형용사 대신 장면, 행동, 숫자, 조건을 보여준다.
- 원문에 없던 비유나 문학적 수사를 억지로 만들지 않는다.

## 제목

- 제목은 작성자가 무엇을 했는지가 아니라 근거가 무엇을 뜻하는지 말한다. 보고서 제목을 작업 일지, 표 설명, 분석 절차처럼 쓰지 않는다.
- “비교했다”, “확인했다”, “살펴봤다”, “분석했다”, “검토했다”, “조사했다”, “봤다”로 끝나는 제목은 먼저 의심한다. 절차를 가르치는 장이 아니라면 결론·판단·긴장·질문으로 다시 쓴다.
- 표본 수, 관측 기간, 비교 기준, 모집단 차이, 출처는 필요하지만 제목의 주인공은 아니다. 이런 조건은 상단 라벨, 부제, 수치 라벨, 방법론 상자, 출처 줄로 내린다.
- 나쁜 예: “Steam 진입 10종을 첫 완결월로 비교했다.” 좋은 예: “Steam 진입 초기 활동은 상위 2종에 집중됐다.”
- 나쁜 예: “상반기 공식 출시 10종을 확인했다.” 좋은 예: “상반기 공식 출시작은 10종이었다.”
- 나쁜 예: “32종을 12개월 동안 봤지만 시장 전체를 봤다는 뜻은 아니다.” 좋은 예: “Steam 공개활동은 시장 전체의 대리값이 아니다.”
- 기술 공유·기술 세미나·교육 자료는 구체성을 유지하되 제목을 억지로 길게 쓰지 않는다. `곡선은 왜 늘어났나`, `파라미터를 왜 의심하나`처럼 화면과 문맥에서 대상이 명확한 짧은 질문도 좋다.
- 기술 제목은 다음 셋 중 가장 짧고 명확한 형식을 고른다: 구체적 질문, 대상·동작 라벨, 결과·범위·한계 문장. 시스템명, 제품명, 프로토콜명, 인터페이스, 명령, 파라미터, 그래프, 필드, 운영 대상을 식별할 수 있어야 한다.
- 설정, 구성, 비교, 필드 설명, 아키텍처, 체크리스트 슬라이드는 명사형이나 짧은 비교 라벨을 우선한다. “Static Exporter와 Dynamic Exporter의 설정·변경 방식을 비교한다”보다 “Static vs Dynamic Exporter”가 낫다.
- direct-technical 자료에서 `-다`로 끝나는 제목을 세 장 연속 쓰지 않고, 전체 제목의 40%를 넘기지 않는다. 결과·한계·결정처럼 문장형이 실제로 더 명확한 장에만 쓴다.
- 나쁜 예: “OIDC는 앞문을 잠그지만 사용자별 namespace 권한을 만들지는 않는다.” 좋은 예: “OpenBao OIDC로 Hubble UI 접근을 인증하고 namespace 권한은 별도로 제어한다.”
- 모든 기술 제목을 `A가 아니라 B`, `A지만 B`, `A일 뿐` 같은 반전 문장으로 만들지 않는다. “앞문을 잠근다”, “증언이다”, “엔진이 된다”, “나침반이 된다” 같은 은유나 훈계형 문장은 구체적 대상과 동작을 대신할 수 없다.
- 브랜드·문화·엔터테인먼트·키노트처럼 감정과 분위기가 발표 목적일 때는 비유적 제목을 쓸 수 있다. 기술 공유에서는 꼭 필요한 비유만 부제나 발표자 노트에 둔다.
- 제목만 순서대로 읽었을 때도 보고서의 주장과 결론 흐름이 보여야 한다. 제목만 읽으면 “무엇을 했는지”만 남는다면 본문 작성 전에 고친다.

## 슬라이드 점검

1. 한국어로 바꿔도 정보가 줄지 않는 영어 표현이 남았는가?
2. 제품명·게임명·수치·날짜·직접 인용이 출처와 일치하는가?
3. 제목이 작성자의 분석 행위를 보고하는 대신 근거의 의미를 말하는가?
4. 제목만 순서대로 읽어도 보고서의 주장과 결론 흐름이 보이는가?
5. 제목이 광고 문구처럼 과장되거나 번역투로 굳어 있지 않은가?
6. 기술 제목에 실제 대상과 동작 또는 경계가 명시되어 있는가?
7. `-다` 종결과 동일한 문장 구조가 연속되거나 과반 가까이 반복되지 않는가?
8. 본문이 발표자가 한 호흡에 읽을 수 있는가?
9. 발표자 노트가 슬라이드 문구를 그대로 반복하지 않는가?

## 최초 렌더 전 동결

사실, 수치, 고유명사, 인용, 슬라이드 순서를 먼저 확정한다. 슬라이드 문구와 발표자 노트는 `humanize-korean`이 있으면 적용하고, 없으면 이 문서 기준으로 다듬는다. 한국어 학습 가이드는 예외다. 완성된 설명을 5,000자 이하의 의미 단위로 나눠 `humanize-korean`을 반드시 적용하고, 다시 합친 뒤 의미가 달라지지 않았는지 확인한다. 가이드는 발표 멘트처럼 줄이지 않는다. 슬라이드에서 생략한 배경과 중간 과정까지 담되, 결론을 먼저 제시하고 어려운 용어는 처음 나올 때 풀어 쓴다. 긴 서론이나 같은 결론의 반복으로 분량을 채우지 않는다.

정밀검증의 최초 렌더 전에 `freeze_authoring_state.py`로 보이는 슬라이드 문구와 노트 해시를 `drafts/research-brief.md`에 동결한다. 이후 CSS, 폰트 선언, 내비게이션 수정은 문구 동결을 깨지 않지만, 실제 문구나 노트가 바뀌면 다시 윤문하고 동결해야 한다.
